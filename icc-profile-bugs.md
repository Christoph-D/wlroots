# ICC Profile Color Accuracy Bugs

## Overview

ICC profiles produce incorrect colors in Sway compared to Windows when using the
same profile on the same display. The documentation itself acknowledges this:
sway-output(5) states "the application of the color profile may be inaccurate."

## Pipeline Summary

1. User config: `output <name> color_profile icc /path/to/profile.icc`
   (`sway/commands/output/color_profile.c`)
2. ICC data is passed to `wlr_color_transform_init_linear_to_icc()`
   (`wlroots/render/color_lcms2.c:27`)
3. lcms2 creates a float transform: synthetic linear sRGB profile → ICC profile
   device encoding, using `INTENT_RELATIVE_COLORIMETRIC`
4. A 33x33x33 3D LUT is evaluated on CPU via `cmsDoTransform()` at each sample
   point (`wlroots/render/vulkan/pass.c:1005-1124`)
5. The LUT is uploaded as a `VK_FORMAT_R32G32B32A32_SFLOAT` 3D texture
6. The `output.frag` shader samples the 3D LUT in the second subpass of a
   two-pass render pipeline

The first pass renders all scene content into a `VK_FORMAT_R16G16B16A16_SFLOAT`
blend image (linear space). The second pass applies the 3D LUT lookup and writes
to the UNORM output framebuffer.

## Bug 1: Missing vcgt (Video Card Gamma Tag) Support

**Severity: High — most likely root cause of incorrect colors**

**File:** `wlroots/render/color_lcms2.c`

### Problem

The code loads the ICC profile and creates an lcms2 color transform but
completely ignores the `vcgt` (Video Card Gamma Tag). Many ICC profiles
generated by calibration tools (DisplayCAL, xrite i1Profiler, Datacolor Spyder,
ArgyllCMS) include a vcgt tag containing per-channel calibration curves that
must be loaded into the display pipeline.

### How it causes wrong colors

The ICC profile's color characterization (TRC curves, matrix, A2B/B2A tables)
describes the display's response **after** the vcgt calibration curves have been
applied. The intended pipeline is:

```
linear sRGB → lcms2 transform → device code values → vcgt → display → correct color
```

- **Windows:** Automatically extracts the vcgt from the ICC profile and loads
  it into the GPU gamma ramp (via the DWM/ICS pipeline), then applies the ICC
  color transform on top. Result: correct colors.

- **Sway:** Skips the vcgt entirely. The lcms2 transform produces device code
  values intended for a calibrated display, but the display is uncalibrated
  (no vcgt applied). Result: wrong colors.

### Proposed fix

In `wlr_color_transform_init_linear_to_icc()` (`color_lcms2.c:27`), after
creating the lcms2 transform:

1. Use `cmsReadTag(icc_profile, cmsSigVcgtTag)` to check for and extract the
   vcgt curves from the ICC profile
2. Convert the vcgt curves to a `COLOR_TRANSFORM_LUT_3X1D`
   `wlr_color_transform` (per-channel 1D LUT)
3. Compose a pipeline: `[lcms2_transform, vcgt_lut]` — the vcgt is applied
   **after** the lcms2 transform because it corrects device code values before
   they reach the display's native response
4. Return the pipeline instead of the bare LCMS2 transform

Alternatively, when the DRM/KMS backend has hardware gamma support
(`GAMMA_LUT` property), the vcgt could be loaded into the hardware gamma ramp.
This would require coordinating with the existing gamma control mechanism in the
scene graph (`wlr_scene.c:scene_output_combine_color_transforms`).

The vcgt curves can be read with:
```c
cmsToneCurve **vcgt = (cmsToneCurve **)cmsReadTag(icc_profile, cmsSigVcgtTag);
if (vcgt != NULL) {
    // vcgt[0], vcgt[1], vcgt[2] are the R, G, B calibration curves
    // Sample each curve to build a LUT_3X1D transform
}
```

### Scope of impact

This affects any ICC profile that includes a vcgt tag with non-identity curves.
Profiles without vcgt (e.g., manufacturer-supplied profiles, hardware-calibrated
monitor profiles, or profiles describing the display's native response) are
unaffected.

## Bug 2: 3D LUT Precision Too Low (33^3)

**Severity: Medium — causes banding and near-black inaccuracy**

**File:** `wlroots/render/vulkan/pass.c:1190`

### Problem

The 3D LUT is fixed at 33x33x33 (35,937 sample points). For complex ICC
profiles with steep nonlinearities, this provides insufficient precision.

### Quantified error (sRGB-like profile example)

The sRGB TRC has a linear segment for x <= 0.0031308 and a power function for
larger values. With 33 samples (spacing = 1/32 = 0.03125), the transition point
falls between sample 0 (x=0.0) and sample 1 (x=0.03125):

| Region        | Linear input | Actual sRGB | LUT approximation | Relative error |
|---------------|-------------|-------------|-------------------|----------------|
| Near-black    | 0.00313     | 0.04045     | 0.00681           | **83%**        |
| Dark          | 0.03125     | 0.11642     | 0.11642           | 0% (exact)     |
| Mid-tone      | 0.10000     | 0.34930     | 0.34870           | 0.17%          |
| Mid-tone      | 0.50000     | 0.73530     | 0.73530           | 0% (exact)     |

The near-black region has extreme errors. Mid-tones and highlights are
acceptable.

### Proposed fix

In `pass.c:1190`, increase the 3D LUT dimension:

```c
vk_transform->lut_3d.dim = 65;  // was 33
```

This increases the LUT to 65^3 = 274,625 samples (7.6x more), which
dramatically improves near-black accuracy at the cost of:

- GPU memory: ~4.4 MB (was ~0.55 MB) for RGBA32_FLOAT
- CPU-side LUT generation: ~275K `cmsDoTransform()` calls (still fast, <100ms)
- GPU bandwidth: negligible (3D texture is cached in VRAM)

Professional color management systems (e.g., madVR, Resolve) typically use 65^3
or 128^3 LUTs.

## Bug 3: Hardcoded Rendering Intent

**Severity: Low — affects only specific profiles**

**File:** `wlroots/render/color_lcms2.c:71`

### Problem

The rendering intent is hardcoded to `INTENT_RELATIVE_COLORIMETRIC`:

```c
cmsHTRANSFORM lcms_tr = cmsCreateTransformTHR(ctx,
    srgb_profile, TYPE_RGB_FLT, icc_profile, TYPE_RGB_FLT,
    INTENT_RELATIVE_COLORIMETRIC, 0);
```

There is no way for the user to specify a different rendering intent.

### Impact

- `INTENT_RELATIVE_COLORIMETRIC` is correct for most display profiles and
  preserves in-gamut colors while adapting the white point
- `INTENT_PERCEPTUAL` may be better for profiles with significantly different
  gamuts (compresses the full gamut to fit)
- `INTENT_ABSOLUTE_COLORIMETRIC` may be preferred for proofing workflows where
  the exact white point must be preserved (no chromatic adaptation)

### Proposed fix

Allow the user to specify the rendering intent in the Sway config:

```
output HDMI-A-1 color_profile icc /path/to/profile.icc relative
output HDMI-A-1 color_profile icc /path/to/profile.icc perceptual
output HDMI-A-1 color_profile icc /path/to/profile.icc absolute
```

Default to `relative` if not specified.

## Notes on Non-Issues (Verified Correct)

The following were thoroughly verified and are **not** bugs:

- **lcms2 transform direction:** linear sRGB → ICC profile is correct. The
  synthetic source profile uses correct D65 white point (0.3127, 0.3291) and
  sRGB primaries with a linear (gamma=1.0) TRC.

- **Matrix encoding:** The `encode_color_matrix()` → `mat3(data.matrix) * rgb`
  path in the output shader correctly maps the CPU-side row-major float[9] to
  GLSL's mat3 when using `row_major` layout. For ICC profiles the matrix is
  identity (the 3D LUT encodes the full transform).

- **3D LUT data layout:** The R/G/B axis mapping (R=width, G=height, B=depth)
  correctly corresponds to the `s/t/p` texture coordinates in
  `texture(lut_3d, vec3(r, g, b))`.

- **LUT coordinate mapping:** `lut_3d_offset = 0.5/dim` and
  `lut_3d_scale = (dim-1)/dim` correctly center samples on texel centers for
  the [0,1] input range.

- **No double gamma:** The scene graph (`wlr_scene.c:2200-2271`) correctly
  uses only the ICC transform when `supplied != NULL` — no additional default
  gamma 2.2 is applied on top.

- **No alpha issues:** The premultiplied → straight → transform → premultiplied
  conversion in the output shader is correct.

- **Push constant layout:** Fragment push constants at offset 80 (after vertex
  data) with `wlr_vk_frag_output_pcr_data` (matrix + offset + scale = 72 bytes)
  match the shader's `layout(offset=80)` declaration.
